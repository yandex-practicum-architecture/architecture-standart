## Задание 2. FURPS+

Заполненная FURPS+ таблица в формате Markdown, учитывая все предоставленные данные, ограничения и цели, с акцентом на архитектурно-значимые требования.

(схема отдельно представлена в файле [/Task2/FURPS+.md](/Task2/FURPS+.md))

```
▌FURPS+ Requirements Table

| F   | Функциональные (Functionality)     | |
| F.1 | Клиент может подать заявку на депозит через сайт, указав ФИО и номер телефона. | Основа для лидогенерации, MVP. Необходима интеграция с колл-центром. |
| F.2 | На сайте отображается список доступных депозитов с актуальными ставками. | Важная информация для принятия решения клиентом. Ставки должны быть актуальными в реальном времени или с минимальной задержкой. |
| F.3 | Клиент может подать заявку на депозит через интернет-банк, указав счёт и сумму. | Предоставление возможности существующим клиентам быстро подать заявку. |
| F.4 | В интернет-банке отображается список доступных депозитов с актуальными и персонализированными ставками. | Персонализация стимулирует клиента к открытию депозита. Необходим механизм расчета персонализированных ставок. |
| F.5 | Операция подачи заявки через интернет-банк подтверждается СМС-кодом. | Повышение безопасности. Использовать существующий СМС-шлюз. |
| F.6 | Менеджер бэк-офиса обрабатывает заявку в АБС. | На этапе MVP обрабатывает вручную. Необходимо обеспечить интеграцию между системой колл-центра, интернет-банком и АБС для передачи информации о заявке. |
| F.7 | В АБС реализована возможность согласования ставки по заявке. | Ручной этап согласования. Важно для гибкости в предложении ставок. |
| F.8 | АБС является источником данных о ставках по депозитам. | Исключение XLS-файлов. Обеспечение единого источника правды для ставок по депозитам. |
| F.9 | Клиент получает СМС-уведомления после подтверждения размера ставки и открытия депозита. | Важная часть коммуникации с клиентом, информирует о статусе заявки. |
| F.10 | Менеджер колл-центра может предложить особые условия после изучения заявки с сайта. | Гибкость в предложении. Необходимо предоставить менеджеру колл-центра доступ к информации о клиенте и возможность изменять условия депозита. |

| U | Удобство использования (Usability) | |
| U.1 | Интерфейс подачи заявки на сайте и в интернет-банке интуитивно понятен и прост в использовании. | Минимизация когнитивной нагрузки на клиента. |
| U.2 | Отклик на действия пользователя (загрузка данных, отправка заявки) должен быть быстрым (миллисекунды). | Важно для положительного пользовательского опыта. Необходимо оптимизировать запросы к базе данных и использовать кэширование. |
| U.3 | Интерфейс соответствует дизайн-системе банка. | Обеспечение консистентности и узнаваемости. |

| R | Надёжность (Reliability) | |
| R.1 | Сервисы должны работать 24/7. | Стандартное требование для банковских систем. |
| R.2 | Доступность сервисов (сайт, интернет-банк) должна составлять 99,9%. | Высокий уровень доступности. Требует резервирования и мониторинга. |
| R.3 | Предусмотрена обработка ошибок и логирование всех операций. | Для отладки, мониторинга и аудита. |

| P | Производительность (Performance) | |
| P.1 | Интернет-банк и сайт должны выдерживать прогнозируемую нагрузку. | Необходимо провести нагрузочное тестирование. |
| P.2 | Интернет-банк и сайт масштабируются горизонтально. | Обеспечение возможности увеличения производительности при росте нагрузки. Необходимо использовать балансировщик нагрузки. |
| P.3 | АБС масштабируется только вертикально. | Ограничение, которое нужно учитывать при проектировании архитектуры. Необходимо оптимизировать запросы к АБС. |
| P.4 | Предусмотрено кэширование данных (ставки депозитов, информация о клиенте). | Снижение нагрузки на базу данных и ускорение доступа к информации.

|
| S | Поддерживаемость (Supportability) | |
| S.1 | Разработана документация для дальнейшего расширения системы. | Важно для долгосрочной поддержки и развития системы. |
| S.2 | По возможности используются существующие технологии, экспертиза в которых уже есть в банке (MS SQL, Oracle, .NET, PHP, React). | Снижение затрат и рисков, связанных с внедрением новых технологий. Использование знакомых технологий упрощает разработку и поддержку. |

| +R | + Ограничения (Restrictions) | |
| +R.1 | Избегать прямой работы интернет-банка с API АБС. | Ограничение, связанное с производительностью и безопасностью АБС. Необходимо использовать посредника (например, API Gateway или Message Queue). |
| +R.2 | Использовать Kafka для очередей сообщений (на перспективу). | Текущая версия платформы интернет-банка несовместима с Kafka. Необходимо учитывать при планировании. |
| +R.3 | Перевод интернет-банка на микросервисную архитектуру возможен только в рамках задачи открытия депозитов (на данном этапе). | Позволит улучшить масштабируемость и гибкость системы, но требует значительных усилий. |
| +R.4 | Защита передаваемых данных (FИО, номер телефона, данные счетов) с помощью шифрования (HTTPS). | Обеспечение конфиденциальности. Использовать SSL/TLS сертификаты. |
| +R.5 | Соблюдение требований регуляторов по защите персональных данных (GDPR, ФЗ-152). | Обязательное требование. Необходимо реализовать меры по защите персональных данных и обеспечить соответствие требованиям законодательства. |
| +R.6 | Обеспечение безопасности от XSS и SQL injection атак. | Стандартные требования безопасности для веб-приложений. |
| +R.7 | Обеспечение защиты от DDoS атак. | Для обеспечения доступности сервисов. |
```

Пояснения и архитектурные выводы:

- Архитектурно-значимые требования: Наиболее важные требования, которые оказывают существенное влияние на выбор архитектурных решений. Это, в частности, требования к производительности (P), надежности (R) и ограничения (+R).
- Интеграция систем: Ключевой вызов - интеграция различных систем (веб-сайт, интернет-банк, АБС, колл-центр) без прямой нагрузки на АБС. Рекомендуется использовать API Gateway и/или Message Queue (Kafka на перспективу).
- Масштабируемость: Необходимо обеспечить горизонтальное масштабирование веб-сайта и интернет-банка, учитывая вертикальное масштабирование АБС.
- Безопасность: Обеспечение безопасности передаваемых данных и защита от атак - критически важные требования.

Рекомендации:

- На этапе MVP максимально использовать существующую инфраструктуру, но предусмотреть возможность масштабирования и интеграции с новыми сервисами в будущем.
- Разработать API Gateway для взаимодействия между интернет-банком и АБС.
- Продумать стратегию миграции данных о ставках в АБС.
- Уделить особое внимание мониторингу и логированию всех операций.
- Обеспечить соответствие требованиям безопасности и защиты персональных данных.

Эта FURPS+ таблица предоставляет структурированное представление требований к системе открытия депозитов и может служить основой для дальнейшей разработки архитектуры и планирования проекта.
